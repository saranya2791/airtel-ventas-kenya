### 5.1 Job Executor and Pipeline Watchdog

| Attribute                | Detail                                                                                                                                                                                                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Name**                 | job\_executor + pipeline\_watchdog +                                                                                                                                                                                                                                                                                |
| **Responsibility**       | Run pipeline work as subprocesses under a **concurrency gate**, track progress, and detect hung stages                                                                                                                                                                                                              |
| **Inputs**               | Job request (instance, stage set, triggering user); subprocess stdout                                                                                                                                                                                                                                               |
| **Outputs**              | Subprocess lifecycle; job status; progress percentage; job history rows                                                                                                                                                                                                                                             |
| **Interfaces**           | OS process spawn; stdout pipe. **No network interface**                                                                                                                                                                                                                                                             |
| **Dependencies**         | Python executable; the agent scripts; job-history store                                                                                                                                                                                                                                                             |
| **Processing logic**     | Two semaphores gate concurrency — **MAX\_CONCURRENT\_LOADS=3** and **MAX\_CONCURRENT\_ROLLBACKS=5**. A job exceeding the limit enters **QUEUED** and waits up to **JOB\_QUEUE\_TIMEOUT\_SECS=3600**. Progress is parsed from PROGRESS: tokens on stdout; timing from TIMING:: tokens                                |
| **Database interaction** | Writes job-history and execution-ledger rows. Does not touch stg\__/tf\__/tgt\_\* directly                                                                                                                                                                                                                          |
| **Configuration**        | Concurrency limits, queue timeout, watchdog timeouts, Python executable path                                                                                                                                                                                                                                        |
| **Security**             | The triggering user's identity is forwarded to the subprocess so every AI call and cost is attributed to a human                                                                                                                                                                                                    |
| **Logging**              | Job start/stop, exit code, queue waits; live console stream to the dashboard                                                                                                                                                                                                                                        |
| **Error handling**       | Non-zero exit is recorded as job failure with the captured output                                                                                                                                                                                                                                                   |
| **Retry**                | **No automatic job-level retry.** A failed run is re-submitted by a human, and Stage 1 resumes from its checkpoint rather than restarting                                                                                                                                                                           |
| **Timeout**              | Two tiers: **Tier A hard ceiling STAGE\_HARD\_TIMEOUT\_SECS=7200** wall-clock per stage subprocess; **Tier B stall detector STAGE\_STALL\_TIMEOUT\_SECS=1200** — no progress token for that long marks the stage hung                                                                                               |
| **Failure behaviour**    | On timeout the subprocess is terminated and the stage recorded as failed. **Design caution:** the stall detector refreshes on progress/timing/stats tokens, so a long-running healthy stream must emit them or it will be killed as hung — the streaming Stage-1 path emits progress tokens for exactly this reason |
| **Performance**          | Concurrency bounded so migration load cannot exhaust the host                                                                                                                                                                                                                                                       |

### 8.1 AI in Stage 3 — the most consequential AI seam

This is the **only** stage where AI is enabled rather than gated-off by default, so it is documented in the greatest depth. **It is invoked conditionally, not per transaction:** a transformation that succeeds makes no AI call at all. The trigger is a SQL failure requiring diagnosis.

| Question                     | Answer                                                                                                                                                                                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **What AI does**             | **Diagnoses a SQL error** and **suggests a corrected SQL statement**                                                                                                                                                                               |
| **What AI does NOT do**      | **It does not apply the fix.** The SDD states explicitly: _"AI SQL-error diagnosis & corrected-SQL suggestion (_ **human applies** _)"_. It does not execute the transformation, write to tf\_\*, alter a stored rule, or decide the run outcome   |
| **Input to AI**              | The database **error message**, the **failing statement** (masked), the relevant **rule definition**, and **schema metadata**                                                                                                                      |
| **Data filtering before AI** | **No result sets and no customer rows.** SQL text and error text only. If the failing statement embeds literal values, the masking chain scrubs them                                                                                               |
| **Masking before AI**        | Full chain §13–§15. Shaped identifiers in error text (e.g. a constraint violation quoting a value) are caught by the deterministic regex layer, which is **always active with no dependencies**                                                    |
| **Prompt construction**      | add\_metadata (schema, rule) + add\_free\_text for the error message, which marks it for the semantic net; reject\_raw active                                                                                                                      |
| **Model invocation**         | Single chokepoint (§16). Deterministic sampling policy for this workflow so a diagnosis is reproducible                                                                                                                                            |
| **Response validation**      | Output guardrails (§17). Additionally, **any SQL the model returns is treated as untrusted text** — it is never executed on the strength of being AI output                                                                                        |
| **Output handling**          | Surfaced on the dashboard as a **recommendation with rationale**, alongside the original rule, for human comparison                                                                                                                                |
| **Approval**                 | **Mandatory human action.** A human reviews, may edit, and explicitly applies. Applying patches the stored rule through the normal metadata path with an audit record. The transformation apply itself sits behind the AWAITING\_APPROVAL workflow |
| **Failure / fallback**       | LLM unavailable or disabled → the stage reports the SQL failure with the raw error and **no suggestion**. Diagnosis is a convenience, never a dependency                                                                                           |
| **Audit logging**            | The AI call in LLM\_INFERENCE\_AUDIT + TOKEN\_USAGE; the human's apply decision in audit\_trail; the rule change in the rule-version history                                                                                                       |

{% hint style="info" %}
**Why this seam is safe** — three independent facts: (1) the AI's output is _text on a screen_, not an executed statement; (2) even if a human applies a wrong suggestion, the run is snapshot-backed and reversible; (3) the AI has no database credential and no network path to the database (HLD §20.5).
{% endhint %}

### 10.4 Trust and Authority Levels — the AI security model in one table

Before the AI components are documented individually, this states **how much each is trusted and how much authority it holds.** It is the clearest single expression of why the AI layer cannot cause a data defect.

| Component                             | Trust level                                   | Authority level                  | Consequence                                                                 |
| ------------------------------------- | --------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------- |
| **Prompt Builder** (§16.1)            | **Deterministic**                             | Gate — can refuse                | Refuses raw records by raising; cannot be persuaded                         |
| **Masking layers** (§15)              | **Deterministic**                             | Transform — always applied       | No dependency to lose on the always-on layers                               |
| **Egress Gateway** (§13)              | **Deterministic**                             | Gate — can block                 | The single chokepoint; CI-guarded against bypass                            |
| **Guardrails** (§14)                  | **Deterministic**                             | Gate — can block or substitute   | Fail-closed under enforce; degrades to regex-only when the engine is absent |
| **LLM Runtime** (§16.2)               | **Deterministic**                             | Policy — retry, shed, break      | Cannot alter content, only whether a call happens                           |
| **LLM / model**                       | ⚠️ **Non-deterministic · UNTRUSTED**          | **NONE**                         | Output is text. It is screened, never executed for being AI output          |
| **Output Validator** (§17)            | **Deterministic**                             | Gate — can block or substitute   | Treats every response as hostile input                                      |
| **AI Control Plane** (§18)            | Deterministic dispatch, **untrusted content** | Read-only via SELECT-only broker | Cannot issue DML/DDL on any path                                            |
| **Human reviewer**                    | —                                             | **AUTHORITATIVE**                | The only actor that may accept an AI suggestion                             |
| **Deterministic ETL engine** (§6–§10) | **Deterministic**                             | **AUTHORITATIVE**                | Sole owner of data movement and database writes                             |

{% hint style="info" %}
**Read the two authoritative rows against the LLM row.** The model holds **no** authority. Everything between the model and the data is deterministic and can refuse. Everything that _can_ change data is either deterministic code or a human.
{% endhint %}

#### 16.3 Safe Mode

The operator's incident lever: disables streaming, forces conservative tool handling, halves concurrency and rejects background requests. Engaged by configuration plus restart, consistent with boot-time immutability.
